- fix: the documentation now says what the run-once handlers actually do. Three documents — the handler reference, the storage developer document, and the templates user document — still claimed that editing an `install.sh`, a `Brewfile`, or a rendered template re-runs it, and that `--provision-rerun` is only for re-running content that has *not* changed. dodot has never done that: it reports `older version` and holds, and `--provision-rerun` is exactly how an edit gets applied. The same inverted claim is corrected in the templates skill and in two shipped proposals (#360).
- fix: every handler table lists every handler. `nix`, `external`, and `gate` were absent from roughly a dozen tables and lists that claimed dodot ships eight handlers; it ships ten. The execution-order document additionally claimed each phase holds a single handler, which was never true of `Filter` (three) and stopped being true of `Provision` when `nix` landed beside `homebrew` — that claim is gone, and the honest note that the order within a phase is undefined replaces it (#360).
- change: the canonical handler table is generated from the registry instead of transcribed. `docs/reference/handler-registry.lex` is rendered from `crates/dodot-lib/src/handlers/catalog.rs` — phase, category, match mode, scope, default patterns and rule priority read straight from `create_registry` and the shipped `[mappings]` defaults — and a test fails when the checked-in page drifts. Nine other pages keep a hand-written roster on purpose, because they name the handlers in the middle of explaining something else; a second test fails when any of them does not mention a registered handler, which is exactly how `nix`, `external`, and `gate` went missing from roster after roster. So a new handler owes the docs a catalog row, a `pixi run gen-docs`, and a line in each of those nine pages — the handler-authoring guide lists them (#360).
- fix: `docs/proposals/shipped/nix.lex` said the content hash is Blake3. It is the first 8 bytes of a SHA-256, rendered as 16 hex characters (#360).
- feat: the `install`, `homebrew`, and `nix` user snippets document what happens when the package manager is not installed — where dodot looks, that it stats rather than spawns, that nothing is recorded and nothing fails, and what `dodot status` says when a receipt outlives the manager that wrote it. The homebrew snippet adds the 5.1.2 version floor and both warning texts, and replaces "macOS-only in practice" with the honest Linux ladder: brew where its prerequisites are acceptable, nix where they are not, `install.sh` where neither fits (#360).
- fix: the nix snippet states plainly that removing a line from `packages.nix` uninstalls nothing — `nix profile remove` appears nowhere in dodot — and names the real homebrew/nix distinction as pinning, written by the user into the manifest, with dodot running `nix profile install --impure` and offering no pinned mode of its own (#360).
- fix: the contributor reference describes the `RunOnceHandler` / `RunOnceCommand` seam. It still documented `InstallHandler` and `HomebrewHandler` as independent structs, which they stopped being when the shared handler landed, and had no section for `nix` at all (#360).
- fix: `dodot status --help` and the status icon legend name `nix`, `external`, and the skipped/gated icon. They listed four of the six icons a file row can carry (#360).
- fix: the configuration and conditional-running user documents are checked against source and stamped `:: verified ::`, the last two user documents this workstream touched without one. Verifying them turned up drift on both: `dodot config schema` was missing from the CLI list and a bare `dodot config` prints help rather than the resolved values; the inheritance section had the layer precedence inverted ("outermost wins" — it is the pack that wins) and listed an `enabled` key that `[preprocessor.template]` does not have; `config list` was described as resolving "a context" when it only ever resolves the root; `force_app`'s 100-entry cap was called a build-time invariant when a test enforces it; and `plist_extensions` named a `.gitattributes` writer that does not exist — dodot prints those lines for you to paste and deliberately never edits the file (#360).
- fix: both status examples in the conditional-running document showed a layout `dodot status` has never produced — a pack header line, the icon after the filename, and a "description" column that only ever appears in `--output json`. Both are replaced with output captured from the binary, in the real column order and the real row order (by pack-relative path). The adopt example claimed `~/.bashrc` adopts as `home.bashrc`; because `bashrc` is on the `force_home` list it adopts as the bare `bashrc` (#360).
- fix: gate label redefinition was documented as always replacing a predicate outright. That is true only for the compiled-in built-in seed; a pack redefining a label the root config defines goes through the normal config merge and overrides only the dimensions it names. The reserved-template-variable and gate-label-name errors were both described as firing "at config load" when they fire when the pipeline or gate table is built — on the first command that plans packs (#360).
- fix: three places in the source told the same kind of lie the documents did — the reserved-vars docstring ("at load time"), the `GpgPreprocessor` docstring (default extensions `["gpg", "asc"]`; the real default is `["gpg"]`, and `.asc` is explicitly warned against), and `dodot config --help`, which advertised `list` as the default subcommand and showed a bare `dodot config` as the way to see resolved configuration (#360).
- fix: the roster drift test reads the roster, not the whole page. It searched each document end to end for every handler name, which meant a handler deleted from a table could still satisfy it on the strength of the name turning up in ordinary prose — `path`, `shell`, and `gate` all do. Each of the nine documents now marks its roster with an invisible `handler-roster` comment (`<!-- … -->` in Markdown, `:: … ::` in lex) and the test compares only what sits between the markers against the registry, so deleting a row fails even when the page still discusses the handler (#360).
