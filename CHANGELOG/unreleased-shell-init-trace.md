- feat: `dodot probe shell-init` now diagnoses the hookup live as well as showing the recorded timings — one report, two halves (#290). By default it spawns your shell once, runs your whole rc under tracing, and reports what `dodot` resolves to *at the hook line*: the hook never ran (dead branch, early `exec`), `dodot` unresolvable there (with the PATH searched and every entry skipped — a dangling symlink is reported, never silently passed over the way `command -v` does), a *different* binary than the one running (both paths, both versions), or the running binary (the hook is sound; look elsewhere). An rc that overrides `PS4` is handled by re-running a temporary *copy* of the rc with a report line inserted before the hook — your real files are never written. The spawn is announced, hard-timeouted, and process-group-killed like every dodot probe. `--no-trace` keeps only the recorded timings, a `<file>` argument stays passive as before, and an unsupported shell, missing rc, or absent hook reports plainly without spawning anything. For the file-source hook, the verdict is about the script *your hook line names* — read off the line itself, not from where `dodot up` would have written one — so a hand-wired hook pointing at a stale copy is judged on that copy; a line dodot cannot resolve without running a shell reports "could not tell which file the hook sources" rather than guessing. PATH resolution follows the shell's own rules for the traced working directory, so empty and relative `PATH` entries pick the same binary your shell would. `status` and `up` are unchanged and still never spawn a shell.
