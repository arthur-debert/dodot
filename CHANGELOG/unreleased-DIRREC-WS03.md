- fix: `dodot adopt` into a pack that already exists no longer writes into the pack before it has decided the run goes ahead. It used to copy every source into its final pack path and only then check for deployment conflicts with your other packs, so a refusal had already written to the pack — and a destination `--force` had overwritten kept the new content even though nothing was adopted. Both destinations now stage the same way: prospective content is copied into a hidden `.dodot-adopt-` directory in your dotfiles root, checked from there, and only then moved into the pack. A refused run leaves an existing pack byte-identical and leaves your original files untouched (#377).
- change: publishing into an existing pack recovers from a failure partway through. Each entry is renamed into place one at a time and each file appears atomically, but the sequence is not atomic — so if any entry fails, `dodot adopt` puts back every entry it had already moved, restores every destination `--force` displaced, removes the directories it created inside the pack and left empty, and reports which entries it restored. Your original files are untouched throughout, because source replacement has not started yet (#377).
- change: `dodot adopt --dry-run` into an existing pack writes nothing into the pack. It used to copy the files in, check, and then remove them again (#377).
- change: a `dodot adopt` killed partway through publishing into an existing pack leaves that pack holding part of the run and leaves its `.dodot-adopt-` directory on disk with any displaced content inside. Recovery is in-process only, and dodot says so rather than implying a crash-safe update: pack discovery ignores the leftover directory, and no later `adopt` publishes from it or deletes it — inspect and remove it yourself (#377).
