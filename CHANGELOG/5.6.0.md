## 5.6.0 - 2026-08-16

- fix: `dodot up`/`down` now write the generated init script atomically (temp sibling + rename) instead of truncating it in place, so a shell that starts while the script is being rewritten can no longer source a partial script — a failure that was silent (a truncated init script is usually still valid shell, so the user lost PATH entries and pack scripts with no error, and the activation evidence at the top of the script still stamped the shell as healthy). The executable mode is applied before the rename, so the visible file is never a non-executable script. The write-atomic guarantee is now a first-class `Fs` operation shared with the Homebrew bootstrap cache (#297)
- feat: on macOS, the generated `dodot-init.sh` now opens with Homebrew's environment, captured from `brew shellenv` by `dodot up`/`down` and cached in dodot's datastore — so brew stays the authority on its own bootstrap and no generation path runs `brew`: the baked-in block is static text, and `dodot init-sh` emits from the cache (#291, #294). The block is emitted verbatim and first, above the PATH additions your packs contribute, which makes a hand-written `001-homebrew` bootstrap pack unnecessary: brew-installed commands are on PATH for every pack script with no ordering work. Per-shell under a guard, so the zsh-only `fpath`/`FPATH` lines never reach `sh` or `bash`. Nothing is emitted when brew is absent (the next `up` heals it) or off macOS; a brew upgrade or a moved prefix is picked up by the next `up`, the same refresh rule as everything else dodot generates. This is the first command execution dodot puts on the shell startup path — brew's own block re-execs `path_helper`, measured at 2-3 ms per shell start; the `brew shellenv` capture itself (10-20 ms each, twice) is paid by `up`/`down`, never by a shell, under either hookup shape. `[shell] homebrew = "off"` turns it off.
- fix: a Homebrew that is installed but fails to answer `brew shellenv` during `dodot up`/`down` — mid-upgrade, non-zero exit, empty output — no longer silently strips the Homebrew block from the init script and deletes the known-good cache. `up`/`down` now warn, quoting brew's exit code or spawn error, and keep the block from the last successful capture (warn-and-keep) so shells keep working through the hiccup; one dialect failing while the other succeeds is handled the same way instead of discarding both. A truly absent brew stays silent and drops the block, exactly as before (#301).
- feat: `dodot probe shell-init` now diagnoses the hookup live as well as showing the recorded timings — one report, two halves (#290). By default it spawns your shell once, runs your whole rc under tracing, and reports what `dodot` resolves to *at the hook line*: the hook never ran (dead branch, early `exec`), `dodot` unresolvable there (with the PATH searched and every entry skipped — a dangling symlink is reported, never silently passed over the way `command -v` does), a *different* binary than the one running (both paths, both versions), or the running binary (the hook is sound; look elsewhere). An rc that overrides `PS4` is handled by re-running a temporary *copy* of the rc with a report line inserted before the hook — your real files are never written. The spawn is announced, hard-timeouted, and process-group-killed like every dodot probe. `--no-trace` keeps only the recorded timings, a `<file>` argument stays passive as before, and an unsupported shell, missing rc, or absent hook reports plainly without spawning anything. For the file-source hook, the verdict is about the script *your hook line names* — read off the line itself, not from where `dodot up` would have written one — and dodot reads that script rather than just checking it exists, so a hook sourcing a copy written by an older dodot reports version skew instead of "sound", matching what the footer says on the same machine. A line dodot cannot resolve without running a shell reports "could not tell which file the hook sources" rather than guessing, and a file with no dodot stamp is reported as unverified rather than certified. PATH resolution follows the shell's own rules for the traced working directory, so empty and relative `PATH` entries pick the same binary your shell would, and only entries where a `dodot` is actually present and still lost the search are listed — missing PATH directories are ordinary and were burying the finding. When the fallback copy is needed, dodot syntax-checks it first: if inserting the report line costs your rc its parse (a `case` pattern, a heredoc), it reports "could not trace" with the shell's own complaint rather than claiming the hook never ran. The announcement says the rc runs up to twice, which is what actually happens. `status` and `up` are unchanged and still never spawn a shell.
- feat: the generated init script now records which dodot wrote it (`DODOT_INIT_VERSION`, plus a version field in the heartbeat), and `up`, `down` and `status` all end on a two-line shell-hookup footer: whether dodot is sourced in new shells, and when it last was, by which dodot (#289). This makes **version skew** visible — shells that load a *different* dodot than the one you run, the failure that used to report as "open a new shell" and could never be fixed by one. "Last loaded" now comes from the heartbeat's mtime rather than the generation written inside it, so it reports when a shell last *ran* the script rather than when `up` last wrote it; evidence left by a pre-5.6 dodot reads as `≤5.5.1`; and after `down` (or in a repo where every pack is ignored) the footer says no packs are deployed rather than claiming a healthy deployment. The two halves of line two always describe the same activation: when your shell reports one dodot and the heartbeat another, the footer names both events rather than pairing one's timestamp with the other's version. And when `up` or `install --write` starts a shell to check the hookup, that shell now reports the version as well as the generation, so a hookup that loads a current script from the *wrong* binary is measured as skew instead of certified healthy. Two things the footer will no longer claim: it does not report a healthy hookup for a terminal session that demonstrably did not load dodot just because some *other* shell did (`up` and `status` now give that session the same answer), and it does not report "sourced in new shells" for a deployment of no packs. And the heartbeat's redirect is `>|` rather than `>`, so `setopt noclobber` in your rc no longer freezes "last loaded" at the first shell you ever opened
