## 5.10.0 - 2026-08-23

- fix: `dodot adopt` no longer leaves a pack behind for a run it then refuses. Adopting into a pack the path implies — `dodot adopt ~/.config/ghostty/config` for a pack `ghostty` that does not exist yet — used to create the pack directory first and check afterwards, so a cross-pack conflict, an unreadable source, or an ignored filename left an empty pack the user never asked for. For that case — an inferred pack that does not exist when the run starts — every refusable check now runs before anything is written, prospective content is staged in a hidden `.dodot-adopt-` directory inside your dotfiles root (which pack discovery skips, so a concurrent `dodot status` sees your packs and not a half-copied one), and the pack is published with a single rename that refuses rather than writing over a pack path that appeared meanwhile: it appears complete or does not appear. Adopting into a pack that already exists is unchanged — it still copies into the pack first and checks for conflicts afterwards (#375).
- fix: `dodot adopt --dry-run` for a pack that does not exist yet writes nothing. It used to create the pack directory and leave it there; it now reports the plan it would carry out and removes its staging directory (#375).
- change: `dodot adopt` refuses an invocation that names a directory and something inside it — `dodot adopt ~/.config/nvim/lua ~/.config/nvim/lua/init.lua` — instead of adopting both. No order of publication comes out right for that pair: replace the directory first and the file resolves back into the pack through the new symlink; replace the file first and publishing the directory buries it. Adopt the outer path alone — adopting a directory already carries its contents. Two sources that don't contain each other but would still land one inside the other in the pack are refused too, and that message names the two pack paths rather than claiming one source contains the other (#375).
- fix: `dodot adopt` no longer evaluates your other packs' templates while checking for deployment conflicts. Checking which paths a pack claims used to render every template and resolve every secret in your repo — writing rendered files and baselines to the datastore, and prompting your secret provider — even for a run that was then refused, and even under `--dry-run`. It now reads those claims the way `dodot status` does, without rendering anything (#375).
- change: `dodot adopt` refuses a run whose deployment-conflict check it cannot complete, instead of reporting the check as clean. A pack's `externals.toml` declares each target it claims inside the file, so the check has to read it; when that manifest exists only as an unrendered `externals.toml.tmpl`, there is nothing to read and the pack's claims stay invisible. Adopt used to read that silence as "claims nothing" and could publish straight into a collision the next `dodot up` then rejected. It now names the file and asks you to run `dodot up` for its pack first. The same holds when the manifest *has* been rendered but its template has changed since — by an edit to the template, or to a `vars` value it interpolates — because what dodot cached is then the targets the pack used to claim rather than the ones it claims now. `--force` does not bypass any of this, for the same reason it does not bypass a conflict (#375).
- fix: `dodot adopt ~/.config/zed/` no longer refuses the whole directory because it holds a `.DS_Store`. A child matching `[pack] ignore` is the noise you already told dodot to leave alone, so adopt now leaves it a real file at its original path, adopts every other child, and reports it once — with the pattern that matched and the configuration file that supplied the list. Naming that path yourself is still refused: adopting it would put an entry in your pack that no later `dodot up` or `dodot status` reads (#376).
- fix: `dodot adopt` reads `[pack] ignore` the way a pack scan does. It used to test a source against the root list *concatenated* with the destination pack's, so a pack whose `.dodot.toml` re-listed the defaults minus one pattern was still refused on a pattern no scan of that pack would apply. A pack-level list replaces the inherited one, and adopt now classifies against that single effective list — the same one `dodot up` applies to that pack — and names which layer supplied it (#376).
- fix: `dodot adopt ~/.config/nvim/.luarc.json` is refused instead of silently producing an unreadable pack entry. A pack's top-level scan skips every name starting with `.` except `.config`, so adopting one used to move the file into the pack and symlink the original at an entry no dodot run reads. A hidden child found while expanding a directory is left where it is and reported, like an ignored one; the refusal for a named one says outright that no config setting changes the rule, because none does (#376).
- change: `dodot adopt` refuses a `.dodot.toml` or `.dodotignore` whether you name it or it turns up expanding a directory. Copying either into a pack would replace that pack's configuration or hide the pack entirely, which is not something to do as a side effect of adopting a directory. When a path matches both this rule and the hidden-name rule, the message is about the reserved name (#376).
- change: `dodot adopt` refuses a directory whose children are all skipped by a discovery rule — including an empty one — and lists each child with the rule that matched it. Reporting every child as left in place and exiting `0` would claim an adoption that never happened (#376).
- change: adopt classifies only where a pack scan reads a name: the first component of the in-pack path, plus the first component inside a `--only-os` directory that passes on this host, since a passing gate directory surfaces its children at pack-root level. `dodot adopt ~/.config/nvim/lua/plugins/init.lua` is refused when `lua` matches a pattern and proceeds when `plugins` or `init.lua` does. Routing prefixes (`_home/`, `_xdg/`, `_app/`, `_lib/`) are ordinary names at that position, so `_home/.gitconfig` and `lua/.hidden.lua` adopt normally. `[mappings] ignore`, `[mappings] skip`, and gate labels dodot defines never participate — they route a file the scan did read; a `_<label>` directory naming a label nothing defines does participate, because a scan fails on it rather than routing it. `--force` changes none of these outcomes (#376).
- fix: `dodot adopt ~/.config/node_modules/settings.json` no longer publishes a pack that later runs skip. The pack directory is a scanned position too — `dodot up` and `dodot status` start by scanning your dotfiles root, and that scan drops directory names matching the root `[pack] ignore` list, names starting with `.`, and names outside the pack-name grammar. Because an inferred pack name comes from the source's own path, adopt could land on one of those and replace your file with a symlink into a pack nothing reads. It now refuses before writing, names the rule, and points at `--into <pack>` (#376).
- fix: `dodot adopt ~/.config/nvim/_bogus/init.lua` is refused instead of breaking the pack it lands in. A pack scan doesn't skip a `_<label>` directory whose label nothing defines — it stops on it, and that error fails the scan of the whole pack, so adopting one would make every later `dodot up` and `dodot status` fail on a pack that read fine before. Found while expanding a directory, it's left in place and reported like an ignored child; defined gate labels and routing prefixes are unaffected (#376).
- fix: `dodot adopt` into a pack that already exists no longer writes into the pack before it has decided the run goes ahead. It used to copy every source into its final pack path and only then check for deployment conflicts with your other packs, so a refusal had already written to the pack — and a destination `--force` had overwritten kept the new content even though nothing was adopted. Both destinations now stage the same way: prospective content is copied into a hidden `.dodot-adopt-` directory in your dotfiles root, checked from there, and only then moved into the pack. A refused run leaves an existing pack byte-identical and leaves your original files untouched (#377).
- change: publishing into an existing pack recovers from a failure partway through. Each entry is renamed into place one at a time and each file appears atomically, but the sequence is not atomic — so if any entry fails, `dodot adopt` puts back every entry it had already moved, restores every destination `--force` displaced, removes the directories it created inside the pack and left empty, and reports which entries it restored. If a step of that recovery fails in turn, `dodot adopt` names the entries it could not put back and where their content is now, and keeps the `.dodot-adopt-` directory rather than cleaning it up, so nothing is deleted. Your original files are untouched throughout, because source replacement has not started yet (#377).
- change: `dodot adopt --dry-run` into an existing pack writes nothing into the pack. It used to copy the files in, check, and then remove them again (#377).
- change: a `dodot adopt` killed partway through publishing into an existing pack leaves that pack holding part of the run and leaves its `.dodot-adopt-` directory on disk with any displaced content inside. Recovery is in-process only, and dodot says so rather than implying a crash-safe update: pack discovery ignores the leftover directory, and no later `adopt` publishes from it or deletes it — inspect and remove it yourself (#377).
- fix: `dodot adopt --force` into an existing pack no longer refuses over a deployment conflict the run itself removes. The conflict check used to read the pack's current entries *and* the adopted ones, so an entry being replaced still claimed the deployment targets it declares today — which could refuse a run whose replacement drops that claim, and left `--force` unable to repair an existing conflict. It now checks the tree publication will leave (#377).
- fix: `dodot adopt` refuses, and says which path is at fault, when a regular file sits where an entry needs an intermediate directory inside the pack, instead of descending past it and failing later with a less clear error (#377).
- change: a `dodot adopt` source that cannot be replaced no longer leaves half its work in the pack. Replacing a source is the last thing adopt does — a symlink at an adjacent temporary name renamed over a file, or a directory renamed aside and symlinked — and when it fails, adopt now undoes the whole of what publication did for that entry: the destination `--force` displaced is renamed back, the published entry and the directories created inside the pack for it are removed, and a pack this run created is removed when no source was replaced at all. It used to remove the entry alone, leaving `nvim/lua/plugins/` behind, an empty inferred pack, and — under `--force` — a destination whose old content was already gone (#378).
- change: `dodot adopt` exits `1` when any source you asked for could not be replaced, and `0` when all of them were. A partial adoption used to exit `0`, so `dodot adopt && …` continued as though the run had done what it said. The result still lists every source, replaced and failed alike. Entries adopt left in place don't move the status: those were never planned for adoption (#378).
- change: sources are independent, and dodot now says which unit is atomic instead of implying the invocation is. A failure on one source is reported and put back; every other source is still attempted and keeps whatever it achieved. A file replacement is one atomic rename, so the original path holds your readable file or the finished symlink and nothing in between; a directory replacement is recoverable rather than atomic, and a process killed mid-way leaves the directory at an adjacent `.dodot-adopt-old-<name>-<id>` path that one `mv` restores. There is no invocation-wide atomic replacement — your `$HOME` and your dotfiles repo can live on different filesystems — and adopt does not claim one (#378).
- fix: a `Brewfile` run no longer upgrades packages you did not ask about. `brew bundle` upgrades every outdated formula it encounters by default, so what reads as "install what this Brewfile declares" could become a long mutating upgrade of unrelated software. dodot now passes `--no-upgrade`; upgrading stays something you ask for, with `brew upgrade` (#358).
- fix: a `Brewfile` run no longer pays for brew's auto-update. The first brew invocation of a day normally runs a `brew update` first — seconds of network traffic upgrading brew and its taps before your packages get a look in. dodot now sets `HOMEBREW_NO_AUTO_UPDATE` for the invocation, so `dodot up` costs what your Brewfile costs (#358).
- change: provisioning handlers can declare environment variables for the command they run. The variables are stated in the handler's compile-time descriptor — no `.dodot.toml` reaches them — and are layered onto the environment dodot itself is running with, so a handler that declares none spawns exactly as before, with your `PATH`, `HOME`, and the rest intact (#358).
- feat: a Homebrew too old for your `Brewfile` is now named before the run, not decoded from a parse error afterwards. brew grew `go`, `cargo`, `uv`, `npm`, and `krew` entries one release at a time, the last two in Homebrew 5.1.2, and dodot's own `HOMEBREW_NO_AUTO_UPDATE` stops brew from quietly updating itself past that line — so `dodot up` asks `brew --version` before running the bundle and reports a brew below 5.1.2 with `brew update` as the remedy. It reports rather than refuses, and hedges: dodot does not read your `Brewfile`, so it says one of those entry types may fail rather than that all of them will — a 5.0.16 already handles `go`, `cargo`, and `uv`, and a file of plain `brew` lines runs fine on an installation older still. A brew at or above the floor says nothing (#359).
- change: the version question is asked only by `dodot up`, only for a `Brewfile` that is actually about to run, and once per machine per run however many packs declare one. `dodot status` and `dodot up --dry-run` still spawn nothing at all — they answer "is brew here?" from the filesystem, which is what keeps them free to run (#359).
- fix: every message about a run-once file (`install.sh`, `Brewfile`, `packages.nix`) now names a flag that does what it claims. Three messages in the executor told users to run `dodot up --force` to apply an edited run-once file; `--force` overwrites pre-existing files at symlink targets and re-fetches externals, and re-runs nothing. They now name `--provision-rerun`, matching the handler status path and `--dry-run` (#356).
- fix: after a real `dodot up`, an edited run-once file's row carries a footnote naming the remedy. The row read `older version (3 lines added, 1 removed)` and stopped there: the executor's remedy message rode on a *successful* operation result, and the post-`up` renderer overlays only failures, so it reached no one (#356).
- fix: `dodot up --no-provision` now reports the files it skipped, labelled `skipped (--no-provision)`, in both the real and `--dry-run` renderings. The flag dropped code-execution handlers before intent generation, so the skipped files produced no row at all in a dry run and showed their untouched datastore state in a real one — with no hint the user had asked to skip them. The label stays distinct from a host-gated file's `gated out (…)`: different conditions, different remedies (#356).
- fix: `--no-provision`'s help text said "Skip install scripts and Brewfile". It covers every code-execution handler, `nix` and `external` included, so an `externals.toml` fetch is suppressed along with the rest (#356).
- fix: `dodot up --help` said code-execution handlers "skip on re-run unless their content has changed" — the inverse of the run-once policy it documents elsewhere. Changed content is exactly what run-once handlers hold: they report `older version` and wait for `--provision-rerun`. The help now separates that from `external`, which really does re-fetch on its own when its sha256 or upstream commit moves (#356).
- fix: the documentation now says what the run-once handlers actually do. Three documents — the handler reference, the storage developer document, and the templates user document — still claimed that editing an `install.sh`, a `Brewfile`, or a rendered template re-runs it, and that `--provision-rerun` is only for re-running content that has *not* changed. dodot has never done that: it reports `older version` and holds, and `--provision-rerun` is exactly how an edit gets applied. The same inverted claim is corrected in the templates skill and in two shipped proposals (#360).
- fix: every handler table lists every handler. `nix`, `external`, and `gate` were absent from roughly a dozen tables and lists that claimed dodot ships eight handlers; it ships ten. The execution-order document additionally claimed each phase holds a single handler, which was never true of `Filter` (three) and stopped being true of `Provision` when `nix` landed beside `homebrew` — that claim is gone, and the honest note that the order within a phase is undefined replaces it (#360).
- change: the canonical handler table is generated from the registry instead of transcribed. `docs/reference/handler-registry.lex` is rendered from `crates/dodot-lib/src/handlers/catalog.rs` — phase, category, match mode, scope, default patterns and rule priority read straight from `create_registry` and the shipped `[mappings]` defaults — and a test fails when the checked-in page drifts. Nine other pages keep a hand-written roster on purpose, because they name the handlers in the middle of explaining something else. Each marks its roster with an invisible `handler-roster` comment (`<!-- … -->` in Markdown, `:: … ::` in lex), and a second test compares what sits between those markers against the registry — scoped to the roster rather than the page, because handler names like `path` and `gate` appear throughout ordinary prose and a page-wide search would stay green even after a handler was deleted from the table it belongs in. That is exactly how `nix`, `external`, and `gate` went missing from roster after roster. So a new handler owes the docs a catalog row, a `pixi run gen-docs`, and a line inside each of those nine rosters — the handler-authoring guide lists them (#360).
- fix: `docs/proposals/shipped/nix.lex` said the content hash is Blake3. It is the first 8 bytes of a SHA-256, rendered as 16 hex characters (#360).
- feat: the `install`, `homebrew`, and `nix` user snippets document what happens when the package manager is not installed — where dodot looks, that it stats rather than spawns, that nothing is recorded and nothing fails, and what `dodot status` says when a receipt outlives the manager that wrote it. The homebrew snippet adds the 5.1.2 version floor and both warning texts, and replaces "macOS-only in practice" with the honest Linux ladder: brew where its prerequisites are acceptable, nix where they are not, `install.sh` where neither fits (#360).
- fix: the nix snippet states plainly that removing a line from `packages.nix` uninstalls nothing — `nix profile remove` appears nowhere in dodot — and names the real homebrew/nix distinction as pinning, written by the user into the manifest, with dodot running `nix profile install --impure` and offering no pinned mode of its own (#360).
- fix: the contributor reference describes the `RunOnceHandler` / `RunOnceCommand` seam. It still documented `InstallHandler` and `HomebrewHandler` as independent structs, which they stopped being when the shared handler landed, and had no section for `nix` at all (#360).
- fix: `dodot status --help` and the status icon legend name `nix`, `external`, and the skipped/gated icon. They listed four of the six icons a file row can carry (#360).
- fix: the configuration and conditional-running user documents are checked against source and stamped `:: verified ::`, the last two user documents this workstream touched without one. Verifying them turned up drift on both: `dodot config schema` was missing from the CLI list and a bare `dodot config` prints help rather than the resolved values; the inheritance section had the layer precedence inverted ("outermost wins" — it is the pack that wins) and listed an `enabled` key that `[preprocessor.template]` does not have; `config list` was described as resolving "a context" when it only ever resolves the root; `force_app`'s 100-entry cap was called a build-time invariant when a test enforces it; and `plist_extensions` named a `.gitattributes` writer that does not exist — dodot prints those lines for you to paste and deliberately never edits the file (#360).
- fix: both status examples in the conditional-running document showed a layout `dodot status` has never produced — a pack header line, the icon after the filename, and a "description" column that only ever appears in `--output json`. Both are replaced with output captured from the binary, in the real column order and the real row order (by pack-relative path). The adopt example claimed `~/.bashrc` adopts as `home.bashrc`; because `bashrc` is on the `force_home` list it adopts as the bare `bashrc` (#360).
- fix: gate label redefinition was documented as always replacing a predicate outright. That is true only for the compiled-in built-in seed; a pack redefining a label the root config defines goes through the normal config merge and overrides only the dimensions it names. The reserved-template-variable and gate-label-name errors were both described as firing "at config load" when they fire when the pipeline or gate table is built — on the first command that plans packs (#360).
- fix: three places in the source told the same kind of lie the documents did — the reserved-vars docstring ("at load time"), the `GpgPreprocessor` docstring (default extensions `["gpg", "asc"]`; the real default is `["gpg"]`, and `.asc` is explicitly warned against), and `dodot config --help`, which advertised `list` as the default subcommand and showed a bare `dodot config` as the way to see resolved configuration (#360).
- fix: nix runs now record the manifest they ran. `run_and_record` used to take the file it ran from the command's *last* argument, a convention `install` and `homebrew` happen to satisfy and `nix` does not — its command ended in `--extra-experimental-features 'nix-command flakes'`, so a nix run wrote no `.snapshot` beside its sentinel and printed `==== <pack> → nix → nix-command flakes` as its progress header. `dodot status --diff` was therefore permanently unavailable for `packages.nix`. Each provisioning handler now declares where its manifest sits in the command's arguments, in a compile-time descriptor registry that no `.dodot.toml` can reach (#354).
- fix: `nix profile install` now runs with `--impure`, without which no manifest shape dodot documents evaluates at all: `--expr` evaluates in Nix's pure mode, which refuses to read both an absolute `packages.nix` path and the `<nixpkgs>` that `{ pkgs ? import <nixpkgs> {} }:` resolves from `NIX_PATH`. Verified against Nix 2.35.2 (#354).
- change: dodot passes your manifest's path to nix as `--argstr manifest <path>` and the wrapper expression reads it as a Nix function parameter, instead of interpolating the path into the expression's text. The expression is now identical for every pack, and a manifest path containing a quote, a backslash, or a `${` needs no escaping into Nix source (#354).
- fix: a failing provisioning command (`install.sh`, `Brewfile`, `packages.nix`) no longer takes the rest of its pack down with it. The failure is reported as an error row against the file that failed, carrying the command, its exit code, and the manager's own output — previously it propagated out of the executor, the whole pack was recorded as failed, and every operation that had already succeeded in it was discarded. Since provisioning runs before symlinks, `$PATH` export, and shell init, a single failing `Brewfile` used to cost a pack all three; now they deploy and report as usual. No sentinel is written for a file that failed, so the next `dodot up` retries it (#353).
- feat: `dodot up` exits 1 when any operation failed and 0 otherwise, instead of always reporting success to the shell — so `dodot up && ./next-step.sh`, a bootstrap script, or an image build stops rather than continuing against a machine that was never set up. 1 is the code `dodot transform check` already uses for its findings. `dodot up --dry-run` attempted nothing and always exits 0 (#353).
